## Verdict

**Njiwa-Mail substantially implements the requested product architecture, but has not yet met the complete product definition of done or demonstrated production readiness.** It is an independent transactional platform with exactly two primary outbound transports, shared API/dashboard and meaningful safety and reliability mechanisms. It is not inherently a Mailcow manager or an empty-VPS-only installer. However, managed domain onboarding still requires a host CLI handoff; delivery evidence is materially deeper for Postfix than arbitrary SMTP; recovery contains coexistence hazards; backward compatibility is not enforced against a historical contract; and independent installation, real Cloudflare-zone behavior and public deliverability remain unverified.

The most urgent implementation finding is outside the guarded installer: **backup/restore infer managed ownership from standard file paths**. On a host using existing Postfix, root backup with queue capture can stop that unrelated mail service; managed restore can overwrite unrelated host configuration. This conflicts with the owner's prohibition on disrupting production mail during operation. It was established by reading the scripts, not by running destructive experiments. See finding F1.

There is also substantial expansion into contacts/campaigns/forms/chat. Preserve existing data and working modules, but focus further effort on transactional completion. Existing project-role enforcement is now merged: the old audit's claim that every signed-in user can open every project is no longer a correct description of runtime authorization.

## Findings and concrete examples

### F1 — Recovery scripts bypass the installer's coexistence boundary (P0)

`backup.sh` gathers `/etc/postfix/main.cf`, `/etc/opendkim` and other standard paths if they exist, with no receipt/marker/profile check. It labels the resulting archive managed; with root and `BACKUP_QUEUE=1`, it stops and starts Postfix [scripts/backup.sh:41](/home/dadi/Projects/ditronics-mail/scripts/backup.sh:41). Thus an existing-SMTP installation on the same host as an unrelated Postfix can inadvertently operate that production service. `restore.sh` verifies checksums, restores the database, then extracts managed configuration at `/`, stops/restarts Postfix and loads firewall configuration without the installer's discovery guards [scripts/restore.sh:15](/home/dadi/Projects/ditronics-mail/scripts/restore.sh:15), [scripts/restore.sh:43](/home/dadi/Projects/ditronics-mail/scripts/restore.sh:43). Checksums prove integrity, not target ownership or permission to replace another mail service. This is a concrete unsafe path, not proof an incident occurred.

### F2 — New managed domains require a manual host handoff (P1)

Verifying a second domain does not install its OpenDKIM key. The UI/service reports `managed_key_missing` and commands containing the claimed domains, selector and submission endpoint [test/mailhost_test.go:88](/home/dadi/Projects/ditronics-mail/test/mailhost_test.go:88), [internal/service/installer_view.go:87](/home/dadi/Projects/ditronics-mail/internal/service/installer_view.go:87). Host apply generates or retains keys [internal/installer/managed/apply.go:212](/home/dadi/Projects/ditronics-mail/internal/installer/managed/apply.go:212), then `RecordManagedInstall` records the configuration and sealed mTLS credentials [internal/service/managed.go:45](/home/dadi/Projects/ditronics-mail/internal/service/managed.go:45). This is a working, guarded manual workflow, not absent DKIM support. The incomplete part is seamless domain-to-host reconciliation; a user must cross to a privileged host command before DNS setup can know the key. Full root privileges in the dashboard would be the wrong corrective design.

### F3 — Generic SMTP works at submission level; evidence depth is Postfix-specific (P1)

A generic Exim server can accept SMTP without Mailcow API provisioning. However, queue-id parsing expects `queued as ...`, log parsing expects `postfix/...`, and the agent runs Postfix commands [internal/service/evidence.go:20](/home/dadi/Projects/ditronics-mail/internal/service/evidence.go:20), [internal/mtaagent/agent_test.go:100](/home/dadi/Projects/ditronics-mail/internal/mtaagent/agent_test.go:100). An Exim-style acceptance ID is not equivalent to this parser. Evidence correlation also selects the newest matching queue ID within seven days without a host/profile key [internal/service/evidence.go:116](/home/dadi/Projects/ditronics-mail/internal/service/evidence.go:116): multiple servers/profile switches can make IDs ambiguous. Existing Postfix logs can be ingested by the same CLI/service if made available; it is inaccurate to claim all existing SMTP is limited to receipts forever. But no general remote evidence adapter is demonstrated. Keep the honest summary: remote acceptance does not prove inbox delivery [internal/service/evidence.go:150](/home/dadi/Projects/ditronics-mail/internal/service/evidence.go:150).

### F4 — Recovery is implemented and partly exercised, but not complete across supported platforms (P1)

The QEMU restore report records recovered database/account, queued deliveries, matching DKIM and reboot persistence, **13/14 with a failed new-send assertion** [docs/evidence/lab/t05.md:1](/home/dadi/Projects/ditronics-mail/docs/evidence/lab/t05.md:1). That explanation is plausible, but no clean rerun report establishes the whole restored workflow. Do not turn 13/14 into an unqualified pass.

There is also an actual portability gap: restore rebuilds fixed `hash:` maps [scripts/restore.sh:55](/home/dadi/Projects/ditronics-mail/scripts/restore.sh:55), whereas installer explicitly supports RHEL-family `lmdb` with its plugin [internal/installer/managed/plan.go:696](/home/dadi/Projects/ditronics-mail/internal/installer/managed/plan.go:696). Configuration rollback exists; do not describe it as missing. What is not established is a reproducible application/database/MTA upgrade and recovery journey across claimed supported platforms with queued/unknown messages preserved.
